# 错误处理与断言策略

> 这份文件定义本项目怎么处理错误。
> 目标是：调试时尽早暴露 bug，发布时行为可预期，不让错误悄悄变成内存踩踏。

## 1. 三类问题

### 1.1 程序内部 bug

例子：
- 不变量被破坏；
- 逻辑上不可能出现的分支；
- 内部数组下标超出自己维护的范围。

处理方式：
- 用 `assert`；
- 只在 Debug 构建中生效；
- 一旦触发，说明代码有 bug，应该修复，而不是让调用方处理。

### 1.2 外部输入错误

例子：
- 矩阵形状不匹配；
- 文件格式错误；
- 用户传入非法参数；
- 模型权重维度和输入不匹配。

处理方式：
- 返回错误码，或者抛出异常；
- 必须让调用方能够处理；
- 不能依赖 `assert`，因为 Release 下 `assert` 会消失。

### 1.3 正常失败

例子：
- 文件打不开；
- 文件不存在；
- 路径错误。

处理方式：
- 返回 `bool` 或错误信息；
- 不要用异常表达可预期的常见失败。

## 2. 本项目当前约定

### 2.1 `Tensor::at`

```cpp
float& at(std::size_t row, std::size_t col);
```

约定：
- `row`、`col` 必须合法；
- 当前用 `assert` 做 Debug 检查；
- Release 下不做边界检查，属于调用方前置条件；
- 如果以后需要安全版本，可以新增 `at_checked()`，不要拖慢热路径 `at()`。

### 2.2 `Tensor::add` / `Tensor::matmul`

当前：
- 用 `assert` 检查形状；
- Release 下 shape 检查会消失。

风险：
- 形状错误可能导致越界读写。

计划：
- M2 之后改成显式检查并抛 `std::invalid_argument`；
- 错误路径只在形状不对时触发，不影响正常路径性能。

### 2.3 `linear`

当前：
- 用 `assert` 检查 `W.rows() == b.cols()`。

计划：
- 同样改成显式检查并抛 `std::invalid_argument`。

### 2.4 文件读取

`load_tensors()`：
- 打开失败返回 `false`；
- 头行格式错误返回 `false`；
- 数据行宽度错误返回 `false`。

这是可预期的外部错误，适合返回错误码。

## 3. 异常类型选择

以后真正使用异常时，按这个表选：

| 情况 | 异常类型 |
| --- | --- |
| 参数非法，例如形状不匹配 | `std::invalid_argument` |
| 下标越界 | `std::out_of_range` |
| 运行时外部错误，例如资源失败 | `std::runtime_error` |
| 内存分配失败 | `std::bad_alloc`，由标准库自动抛出 |

## 4. 测试策略

Catch2 提供异常断言：

```cpp
CHECK_THROWS_AS(t.add(other), std::invalid_argument);
CHECK_THROWS_AS(t.at(999, 0), std::out_of_range);
```

以后把形状错误改成异常后，必须补对应测试。

## 5. 性能原则

- 公开边界检查：对外 API 可以做；
- 最内层循环不做异常检查和分支；
- `at()` 这种热路径保持简单；
- 需要安全访问时，提供单独函数，例如 `at_checked()`。

## 6. 当前状态

- Debug 下：主要依赖 `assert`；
- Release 下：形状错误和越界不会主动报错；
- 文件读取：已经使用 `bool` 返回值；
- 异常改造：列入后续工程化任务。

这份策略固定后，后续所有错误处理都按它执行。
